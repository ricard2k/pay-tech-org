# Authorization Request Cryptogram and Authorization Response Cryptogram

In the world of EMV smart chip card transactions, **ARQC** stands for **Authorization Request Cryptogram** and **ARPC** stands for **Authorization Response Cryptogram**.

These two cryptograms act as a secure, end-to-end cryptographic handshake between the physical chip on your card and the issuing bank's server. They ensure that neither the transaction request nor the bank's response can be intercepted, altered, or replayed by a fraudster.

The mathematical generation of an **ARQC (Authorization Request Cryptogram)** is a multi-step block-cipher process governed strictly by the **EMV 4.3 Specifications (Book 2 - Security and Key Management)**.

Unlike a simple static hash, the ARQC formula relies on **Symmetric Block Encryption (3DES or AES)** acting as a **Message Authentication Code (MAC)** algorithm. It takes a variable-length block of dynamic transaction data, condenses it, and signs it using a temporary session key.

## The Inputs: The EMV Data Element Block

Before any math occurs, the EMV chip constructs a fixed, contiguous binary string out of the transaction variables. This data string is collectively called the **Minimum Input Data Element Block** (dictated by the card profile’s CDOL1 – Card Risk Management Data Object List 1). It usually consists of:

- **Amount, Authorized** (6 bytes, numeric)
- **Amount, Other** (6 bytes, numeric)
- **Terminal Country Code** (2 bytes, numeric)
- **Transaction Currency Code** (2 bytes, numeric)
- **Transaction Date** (3 bytes, numeric)
- **Transaction Type** (1 byte, numeric)
- **Unpredictable Number** (4 bytes, random binary generated by the terminal to prevent replay attacks)
- **Application Transaction Counter (ATC)** (2 bytes, binary counter ticking up by 1)
- **Terminal Verification Results (TVR)** (5 bytes, binary flags indicating terminal health check outcomes)

These fields are concatenated into a single data block, which we will call **M**.

## Step 1: Padding the Data String

The concatenated transaction block M can be of varying lengths depending on the card's configuration, but the underlying block cipher requires the data to be perfectly aligned to **8-byte (64-bit) boundaries** for 3DES, or **16-byte (128-bit) boundaries** for modern AES profiles.

EMV uses standard **ISO/IEC 9797-1 Padding Method 2**:

1. A single mandatory byte valued at hex `0x80` is appended to the end of the transaction string $M$.
    
2. Hex `0x00` bytes are continuously appended after the `0x80` byte until the entire string's length is a perfect multiple of 8 (or 16) bytes.

$$M_{padded} = M \mathbin\Vert \text{0x80} \mathbin\Vert \text{0x00...0x00}$$

This padded string is then sliced evenly into sequential data blocks: $D_1$, $D_2$, $D_3$, ..., $D_n$.

## Step 2: The CBC-MAC Algorithmic Loop

The math uses a **Cipher Block Chaining Message Authentication Code (CBC-MAC)** loop. This means the result of encrypting the _first_ block is combined with the _next_ block before it is encrypted, making every single digit in the payload mathematically dependent on all preceding digits.

The formula runs through the blocks using the derived **Session Key (SK)** (which was derived from the master MDK using the card's current ATC):

$$\begin{aligned}
O_{1}&=Encrypt_{DES}(D_{1},SK_{Left}) \\ 
O_{2}&=Encrypt_{DES}(O_{1}\oplus D_{2},SK_{Left}) \\ 
O_{3}&=Encrypt_{DES}(O_{2}\oplus D_{3},SK_{Left}) \\ 
&\ \ \vdots \\ 
O_{n}&=Encrypt_{DES}(O_{n-1}\oplus D_{n},SK_{Left})
\end{aligned}
$$

Where:
- $Encrypt_{DES}$ is a single-DES encryption loop (8-byte block size).
- $\oplus$ represents a bitwise **XOR** operator.
- $SK_{Left}$ is the first 8-byte half of the 16-byte dynamic session key.

## Step 3: Triple-DES Triple-Wrap (The Final Signature)

Once the CBC loop reaches the absolute final block $(O_{n})$, a single DES encryption isn't cryptographically secure enough. The EMV formula executes a full **Triple-DES (3DES) cycle** exclusively on this final output block to lock the entire sequence securely.

Using both halves of the Session Key $SK_{Left}$ and $SK_{Right}$, the formula calculates:

$$
Final\ Block =Encrypt_{DES}\Big(Decrypt_{DES}\big(O_{n},SK_{Right}\big), SK_{Left}\Big)
$$

## Step 4: Truncation to the ARQC

The output of that final 3DES calculation is a secure 8-byte (64-bit) binary block. Because a full 64-bit signature is too heavy to routinely pass back and forth across fast, congested legacy telecom networks during live clearings, EMV truncates it.

- The system takes the leftmost **8 bytes** (or 4 bytes depending on the exact chip protocol profile, usually EMV tag `9F26`).
- This exact truncated signature becomes the **ARQC**.

When the merchant terminal routes your transaction to the cloud, it passes this binary signature along with the raw fields (Amount, ATC, Unpredictable Number). The bank's backend HSM duplicates this mathematical chain using its own master **MDK**; if its final calculated block matches the card's transmitted ARQC, the transaction is cryptographically proven to be genuine.
